# SQL-запросы для мониторинга базы

В этом каталоге лежат готовые запросы к PostgreSQL для проверки состояния
каталога аниме. Они помогают ответить на вопросы:

- сколько всего тайтлов и сколько из них заглушек;
- у скольких тайтлов нет постера или постер не скачался;
- сколько записей обогащения завершились ошибкой;
- как данные распределены по пользовательским спискам;
- какие тайтлы чаще всего встречаются в списках и какие стоит обогащать первыми.

Все запросы выполняют только `SELECT` и не меняют данные. Их можно запускать
на рабочей базе, но на больших таблицах подсчёт занимает время. Лучше делать
это вне активного импорта или обогащения.

## Как запускать

Через `psql` из корня проекта:

```powershell
psql -h localhost -p 5433 -U postgres -d AnimeQuiz -f scripts\sql\01_overview.sql
```

Можно открыть файл в pgAdmin, DBeaver, Adminer или другом клиенте и выполнить
его целиком.

При сборке app-image каталог `scripts` копируется рядом с приложением, поэтому
эти файлы будут доступны и в `%USERPROFILE%\Desktop\AnimeQuiz\scripts\sql`.

Каждый файл начинается со строки:

```sql
SET search_path TO main;
```

Если схема называется иначе, замените `main` на своё имя или удалите эту
строку, если схема уже выбрана в клиенте.

## Файлы

| Файл | Что показывает |
|---|---|
| `01_overview.sql` | Общая сводка: всего тайтлов, активные/неактивные, `stub`/`partial`/`full`, состояния постеров, ошибки и попытки обогащения, источники ID, сироты, связи с пользователями. |
| `02_completeness_poster.sql` | Таблица «полнота данных × состояние постера»: сколько тайтлов в каждой комбинации. |
| `03_by_user.sql` | По каждому пользователю: сколько тайтлов в списке, сколько заглушек, сколько без постера, сколько постеров с ошибкой. |
| `04_stubs.sql` | Список заглушек с ID, названиями, ошибками обогащения и числом пользовательских списков. По умолчанию — 200 строк. |
| `05_top_titles.sql` | Топ-50 тайтлов по числу списков пользователей. |

## Что означают поля

### `anime.completeness`

| Значение | Смысл |
|---|---|
| `stub` | Заглушка. Запись создана из списка пользователя, но данные ещё не подтянуты. Обычно называется `Unknown #<id>`. |
| `partial` | Часть данных уже получена, но запись ещё не считается полной. |
| `full` | Полные данные получены от Shikimori или YummyAnime. |

В профиле пользователя заглушки скрываются, пока у тайтла не появятся данные
и постер.

### `anime.poster_status`

| Значение | Смысл |
|---|---|
| `pending` | Постер ещё не обработан. |
| `ready` | Постер скачан и готов к показу. |
| `failed` | Скачать постер не удалось. |
| `no_image` | У тайтла нет URL постера. |

Отдельно стоит учитывать постеры, у которых `poster_url` содержит
`missing_preview`: это URL-заглушка, а не настоящая картинка.

### Обогащение

| Поле | Смысл |
|---|---|
| `enriched_at` | Когда тайтл последний раз проходил обогащение. `NULL` — ещё не проходил. |
| `enrich_attempts` | Сколько было попыток обогащения. |
| `enrich_last_error` | Текст последней ошибки. |
| `enrich_next_at` | Когда планируется следующая попытка после ошибки. |

Большое число записей с `enrich_attempts >= 5` и заполненным
`enrich_last_error` означает, что источники стабильно не отдают данные или
сломалась интеграция.

## На что смотреть в первую очередь

1. **Доля `stub`.** Если она растёт после импорта — фоновое обогащение не
   успевает за загрузкой списков.
2. **`poster_status = 'failed'`.** Это тайтлы, у которых не скачалась картинка.
3. **`enrich_next_at` в прошлом.** Записи пора обрабатывать, но очередь стоит.
4. **`in_user_lists` у заглушек.** Чем больше пользователей ждут тайтл, тем
   выше приоритет его обогащения.
5. **Сироты.** Тайтлы, которых нет ни в одном списке, можно проверить
   отдельно: возможно, это остатки старых импортов.

## Схема базы

Запросы используют таблицы `anime` и `user_anime` из миграции
`V4__anime_catalog.sql`. Если в вашей базе есть более новые миграции, которые
добавляют поля к этим таблицам, запросы продолжат работать: они читают только
перечисленные выше колонки.
